# Notification Platform

## Функциональные требования

### 1. Единая точка отправки уведомлений

Любая команда банка (платежи, кредиты, маркетинг и пр.) отправляет уведомления через единый API платформы, указывая тип уведомления, получателя, канал (или автовыбор) и содержание сообщения.

### 2. Многоканальная доставка

Система доставляет уведомления по трём каналам: push, SMS, email. Выбор канала определяется типом уведомления, настройками пользователя и доступностью канала.

### 3. Управление подписками пользователя

Пользователь может отключить маркетинговые уведомления и часть сервисных (например, промо-напоминания). Транзакционные уведомления и критичные сервисные (безопасность, подтверждение входа) отключить нельзя.

### 4. Приоритизация по типу уведомления

Транзакционные уведомления обрабатываются с наивысшим приоритетом. Массовая маркетинговая рассылка не должна задерживать доставку критичных уведомлений.

### 5. Автоматический failover между каналами

При неуспешной доставке транзакционного уведомления по основному каналу система автоматически переключается на резервный канал (push -> SMS -> email).

### 6. Дедупликация уведомлений

Система позволяет предотвращать повторную отправку одного и того же уведомления пользователю - даже при retry и failover.

### 7. Массовые рассылки

Система поддерживает массовые рассылки без деградации остального трафика.

## Нефункциональные требования

### 1. Задержка доставки (Latency)

| Тип уведомления | SLA (p99) |
|---|---|
| Транзакционные | <= 1 с от приёма запроса до передачи провайдеру |
| Сервисные | <= 5 с |
| Маркетинговые | <= 30 мин |

### 2. Пропускная способность

- Суточный объём: ~30 млн уведомлений/день.
- Средний RPS: ~350.
- Пиковый RPS: до 3k.

### 3. Доступность

- SLA для транзакционных уведомлений: >= 99.9% (MC).
- SLA для транзакционных уведомлений: >= 99.6% (BC).

### 4. Надёжность доставки

- Транзакционные уведомления: delivery rate >= 99.99%.
- Сервисные: ≥ 99.9%.
- Маркетинговые: ≥ 95%.

### 5. Наблюдаемость

- Трассировка жизненного цикла каждого уведомления (от приёма до подтверждения доставки).
- Метрики в реальном времени: latency, delivery rate, error rate, failover rate в разрезе типов и каналов (чтобы можно было настроить алерты).

## Архитектурно значимые требования (ASR)

### 1. Низкая задержка доставки транзакционных уведомлений

Связанные требования:
- Ф4: приоритизация
- НФ1: latency <= 1 с p99

Почему влияет:
- Требует выделенного fast-path для критичных уведомлений с минимальным количеством промежуточных шагов.
- Определяет необходимость приоритетных очередей или отдельных топиков/пулов обработки.
- Запрещает синхронную обработку через общую очередь с маркетинговым трафиком.

### 2. Гарантированная доставка с кросс-канальным failover

Связанные требования:
- Ф5 (failover)
- Ф6 (дедупликация)
- НФ4 (delivery rate >= 99.99%).

Почему влияет:
- Требует хранения состояния доставки каждого уведомления (state machine).
- Определяет модель взаимодействия между компонентами: нужен механизм отслеживания результатов доставки и принятия решения о fallback.
- Вводит требование идемпотентности на уровне канальных адаптеров для предотвращения дублирования при retry/failover.

### 3. Предотвращение дублирования уведомлений

Связанные требования:
- Ф6 (дедупликация)
- НФ7 (идемпотентность)

Почему влияет:
- При наличии retry и failover один запрос может породить несколько попыток отправки. Необходим механизм exactly-once semantics или at-least-once + дедупликация. Это влияет на выбор брокера сообщений, стратегию хранения состояния и контракты между сервисами.

## Ключевые архитектурные вопросы

### 1. Как обеспечить изоляцию трафика разных приоритетов?

Порождающие требования: 1 (low latency)

Почему важен: Если транзакционные и маркетинговые уведомления идут через одну очередь, массовая рассылка (до 1 млн сообщений) заблокирует обработку критичных уведомлений.

### 2. Какую модель координации failover использовать - оркестрацию или хореографию?

Порождающие требования: 2 (гарантированная доставка), 3 (дедупликация).

Почему важен: Оркестратор проще в отладке и наблюдаемости, но может стать узким горлышком. Хореография лучше масштабируется, но усложняет отслеживание состояния и предотвращение дублей. Выбор определяет всю структуру взаимодействия компонентов.

### 3. Как интегрироваться с нестабильными внешними провайдерами без потери уведомлений?

Порождающие требования: 2 (failover), 3 (availability), 4 (reliability).

Почему важен: Провайдеры SMS/email/push имеют разные SLA, rate limits и модели подтверждения доставки. Нужно определить: таймауты ожидания ответа, стратегию retry, момент переключения на fallback-канал, и как обрабатывать ситуацию, когда провайдер принял сообщение, но не доставил.

## Архитектурные последствия ASR

### 1. Низкая задержка транзакционных уведомлений

Последствия:
- Выделенный fast-path: отдельный Kafka-топик (или отдельная очередь) для транзакционных уведомлений
- Отдельный пул воркеров для обработки критичного трафика
- Минимизация количества I/O-операций на критичном пути (кэширование настроек пользователя в Redis)
- Коннекты к провайдерам в пуле
- Все внешние вызовы медленных внешних систем на критичном пути асинхронные

### 2. Гарантированная доставка с failover

Последствия:
- ДКА для каждого транзакционного уведомления
- Персистентное хранилище состояния (скорее всего PostgreSQL)
- Механизм таймаутов: если подтверждение доставки не получено за N секунд - считать канал failed.
- Ключ идемпотентности на уровне каждого канального адаптера.
- DLQ для уведомлений, исчерпавших все каналы.
- Outbox pattern или transactional messaging для гарантии консистентности между БД и брокером.

### 3. Изоляция массовых рассылок

Последствия:
- Архитектурное разделение на минимум два потока: high-priority (транзакционные + сервисные) и low-priority (маркетинговые).
- Отдельные Kafka-топики с отдельными consumer groups для каждого приоритета.
- Rate limiter на маркетинговом потоке (ограничение RPS к провайдерам).
- Backpressure-механизм: маркетинговая рассылка замедляется при приближении к лимитам провайдера, но не влияет на транзакционный поток.

## Архитектурные решения, которые НЕ подходят

### 1. Синхронная обработка всех уведомлений через REST-цепочку

API-запрос → синхронный вызов в Delivery Service → синхронный вызов провайдера → ответ клиенту.

Нарушаемые ASR: 1 (latency).

Почему не подходит:
- Синхронная цепочка делает latency зависимой от самого медленного звена (внешний провайдер может отвечать 2-5 с).
- При недоступности провайдера запрос зависает - нет возможности failover без асинхронной обработки.
- Массовая рассылка на 1 млн пользователей потребовала бы 1 млн одновременных HTTP-соединений, что нереалистично.
- Отсутствует буфер (очередь) - при всплеске нагрузки система деградирует целиком.

### 2. Единая очередь для всех типов уведомлений (без приоритизации)

Все уведомления (транзакционные, сервисные, маркетинговые) попадают в одну очередь и обрабатываются в порядке поступления.

Нарушаемые ASR: ASR-1 (latency).

Почему не подходит:
- Маркетинговая рассылка на 1 млн получателей создаст очередь из 1 млн сообщений. Транзакционное уведомление, поступившее в этот момент, встанет в конец очереди и будет обработано с задержкой в минуты или часы.
- Даже с priority queues в рамках одной очереди - есть ограничения производительности и сложность гарантирования SLA.
- Нет физической изоляции - сбой в обработке маркетинговых сообщений (например, ошибка шаблонизации) может повлиять на весь поток.

## Неопределённости и архитектурные риски

### 1. Реальные SLA и поведение внешних провайдеров

Неизвестны:
- Точные показатели latency, delivery rate и error rate провайдеров SMS, email и push
- Их rate limits
- Как они ведут себя при пиковой нагрузке
- Есть ли у них гарантии at-least-once delivery

Как проверить:
- Провести нагрузочное тестирование с реальными провайдерами в staging-среде.
- Собрать метрики за 2-4 недели в production-like условиях.
- Запросить у провайдеров формальные SLA и лимиты.
- На основании данных определить таймауты failover и стратегию retry.

### 2. Модель подтверждения доставки push-уведомлений

Неизвестно: push-уведомления не гарантируют доставку до устройства - они подтверждают только приём в облако. Нет надёжного способа узнать, доставлено ли push-уведомление пользователю.

Как проверить:
- Реализовать подтверждения в приложении: при открытии push-уведомления мобильное приложение отправляет callback в платформу.
- Оценить процент "тихих потерь" (push принят, но не доставлен) на реальных данных.
- На основании этих данных - решить, считать ли push надёжным основным каналом для критичных уведомлений или использовать его только как дополнительный.
