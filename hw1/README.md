# ДЗ1

## Домены в задаче

1. Auth

Тут авторизация и аутентификация, и все, что с ними связано: например, авторизация API токенов или токенов oauth.

2. Управление аккаунтами

Здесь все профили на платформе со своими настройками. Например поменять пароль или почту, настроить уведомления или средства оплаты. Для продавцов - например, приложить дополнительные документы, если надо

3. Управление каталогом

Тут продавцы создают/редактируют все, что выставляется на продажу: описания товаров, фотографии, цены. Если есть модерация товаров, она тут же.

4. Логистика

Тут все, связанное с физическим расположением товаров. Если продавец удалил товар из каталога, это не значит, что он испарится из складов.

5. Поиск

Все что связано с поиском товаров.

6. Discovery

Все, что связано с обнаружением товаров, например, персонализированная лента или персональные предложения в уведомлениях.

6. Обработка заказов

Тут пользователь кладет товары в корзину, оформляет товары, и отслеживаются их статусы.

7. Платежи

Здесь скорее хранилище информации о платежах и балансах пользователей, так как реальными транзакциями занимается внешняя система.

(*) По идее так же, как и каталог и логистика находятся раздельно, надо бы отдельный домен для бухгалтерского учета, но че-то и так уже сложно выходит

8. Уведомления

Все виды уведомлений (об изменениях статусов заказов, персональных рекомендаций и т. п.) живут здесь.

9. Сбор данных для аналитики

Сбор данных о пользователях для обучения моделей, антифрода, проведения A/B тестов и подобного.

## Варианты

### Простой дизайн

С4 диаграмма в `coughing-baby.mmd`.

#### Сервисы

- Сервис для авторизации/аутентификации
- Сервис для менеджмента аккаунтов
- Сервис каталогов (в одном сервисе домены каталога и логистики)
- Сервис поиска (поиск + обнаружение)
- Сервис обработки заказов и платежей (в одном т.к. вероятно не сами реализуем эквайринг)
- Сервис уведомлений
- Сервис сбора данных (ingest для будущей аналитики + метрики)

Данные у каждого сервиса свои: у авторизации выданные токены, а аккаунтов все, что с этим связано, у каталогов товары, и т. д.
NOTE: сервис поиска использует какой-то свой индекс (типа ElasticSearch), который наполняется данными из сервиса каталогов.
В таком случае все еще у каждого сервиса свои данные, но не значит, что данные строго изолированы внутри каждого сервиса.

#### Взаимодействия

Здесь все синхронные, кроме сбора метрик.

#### Плюсы

- Все просто, вся система это набор пар сервис-бд.

- Без асинхронных взаимодействий, такое проще дебажить, логировать и трассировать.

#### Минусы

- Требования к поиску и рекомендациям товаров разные, складывать их в один сервис не очень хорошо.

- Из-за синхронных взаимодействий некоторые действия придется делать через БД. Это проще и дает гибкость,
и на небольших нагрузках лучше, чем брокер сообщений, поэтому в этом варианте без него.
Но при увеличении нагрузки не прокатит. Также может сломаться при всплеске траффика.

### Сложный дизайн

С4 диаграмма в `hydrogen-bomb.mmd`.

#### Сервисы

В своих собственных доменах:

- Сервис для авторизации/аутентификации
- Сервис для менеджмента аккаунтов
- Сервис логистики
- Сервис платежей
- Сервис обнаружения
- Сервис уведомлений
- Сервис сбора метрик

Также отдельно:

Домен каталогов:

- Сервис каталогов
- Сервис купонов/промоакций (каталоги редактирует продавец, купоны/акции идут от самого маркетплейса)
- Сервис модерации

Домен поиска:

- Сервис поиска (API)
- Сервис выгрузки данных каталогов и загрузки в поиск (не совсем сервис,
не придумал, как еще назвать)

Домен обработки заказов:

- Сервис корзины
- Сервис заказов

NOTE: предполагаю, что метрики идут куда-то в открытое для исследования хранилище.
Если нет, и все свое, то нужен еще сервис-обработчик метрик, но это уже (как-будто) не входит в дизайн.

#### Взаимодействия

Синхронные: оформление заказа т.к. атомарная операция.

Асинхронные: снапшоты каталогов для поиска, обновления настроек формирования рекомендаций (он не лезет каждый
раз в сервис профилей, у него закэширована информация), отправка уведомлений, сбор данных для аналитики,
список платежей/транзакций.

#### Плюсы

- Больше разделение ответственности, следовательно более точечные релизы/тесты, проще изолировать проблему
- Лучше будет скейлиться, так как не завязываемся на скорость реляционной БД в узких местах

#### Минусы

- Куда сложнее
- Больше сервисов = больше кода, больше нужно людей, больше железа

## Выбор дизайна

Разумеется лучше второй, так как с первым не получится освоить бюджет целиком.
