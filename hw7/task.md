# **Домашнее задание №7**

## **CI/CD, Testing & Observability**

Цель задания — настроить **полноценный CI/CD pipeline** с автоматическим
тестированием, мониторингом и нагрузочным тестированием для вашей
микросервисной системы из предыдущих домашних заданий.

Задание можно реализовывать на любом языке программирования и любом
фреймворке. Если предыдущее домашнее задание не сдано или не реализовано
в должной мере для сдачи текущего домашнего задания разрешается
произвести доработки предыдущего дз.

Задание разделено на **три блока по возрастанию сложности**:

- **1–4 балла** — CI pipeline, тестирование и базовые метрики

- **5–7 баллов** — визуализация, инфраструктурный мониторинг,
  нагрузочное тестирование

- **8–10 баллов** — комплексная проверка под нагрузкой, алерты, SLI/SLO

Блоки оцениваются **последовательно**: пункты следующего блока
проверяются только при полном выполнении предыдущего. Например, если из
блока 1–4 выполнены только 3 пункта из 4, задания на 5–7 баллов не
оцениваются.

## **1–4 балла**

### **1. CI pipeline (1 балл)**

Необходимо настроить CI pipeline, который автоматически запускается при
push или PR.

**Требования:**

- CI запускается **автоматически** (push / PR).

- В пайплайне есть шаги:

  - **build** — сборка всех ваших сервисов

  - **unit tests** — модульные тесты для каждого сервиса

  - **integration tests** — интеграционные тесты (см. п.2)

- Пайплайн **падает при любой ошибке**.

- Конфигурация CI хранится в репозитории (`.github/workflows/ci.yml`,
  `.gitlab-ci.yml` или аналог).

- Логи пайплайна доступны и читаемы.

> **Важно:** студент самостоятельно проектирует структуру пайплайна —
> какие шаги параллельны, какие последовательны, как организованы jobs.
> Конкретный CI-инструмент — на выбор (GitHub Actions, GitLab CI,
> Jenkins и т.д.).

------------------------------------------------------------------------

### **2. Интеграционные тесты сервисов (1 балл)**

Необходимо реализовать интеграционные тесты, которые проверяют
взаимодействие между вашими сервисами.

**Требования:**

- Тесты поднимают **зависимости** (Docker / Testcontainers).

- Проверяют **взаимодействие между сервисами**, а не один сервис в
  изоляции. Например: запрос проходит через API-сервис, вызывает
  внутренний сервис по gRPC/HTTP/Kafka и результат сохраняется в БД.

- Тесты изолированы (не зависят от порядка выполнения других тестов).

- Тесты очищают состояние после выполнения.

- Тесты запускаются одной командой и возвращают exit code 0 при успехе,
  1 при ошибке.

------------------------------------------------------------------------

### **3. End-to-End тест системы (1 балл)**

Необходимо реализовать E2E тест, который проверяет полный
пользовательский сценарий вашей системы.

**Требования:**

- Тест запускает **реальный пользовательский сценарий** через ваш API.

- Проверяет результат в **конечном хранилище** (ваша БД).

- Тест покрывает минимум **один полный сценарий** из предметной области
  вашей системы.

- Тест проверяет **сквозную логику**, а не отдельные сервисы.

**Требования к проверкам:**

- Проверка HTTP/gRPC статусов.

- Проверка тела ответа (поля, типы данных).

- Проверка состояния в БД (запись создана, обновлена, удалена).

Примеры сценариев зависят от вашей системы:

- **Marketplace:** создать товар → создать заказ → проверить
  резервирование stock в PostgreSQL.

- **Flight Booking:** создать рейс → забронировать → проверить, что
  места зарезервированы через gRPC и записаны в обе БД.

- **Online Cinema:** отправить событие → проверить, что оно прошло через
  Kafka и появилось в ClickHouse.

- **Warehouse:** отправить PRODUCT_RECEIVED → проверить остатки в
  Cassandra.

------------------------------------------------------------------------

### **4. Prometheus + базовые метрики сервисов (1 балл)**

Каждый ваш сервис должен экспортировать метрики в Prometheus.

**Требования:**

- Каждый сервис экспортирует метрики по endpoint `/metrics`.

- Минимум метрик на каждый сервис:

|                                                   |           |                                    |                         |
|---------------------------------------------------|-----------|------------------------------------|-------------------------|
| Метрика                                           | Тип       | Labels                             | Описание                |
| `http_requests_total` (или аналог для gRPC/Kafka) | Counter   | `method`, `endpoint`, `status`     | Количество запросов     |
| `http_request_errors_total`                       | Counter   | `method`, `endpoint`, `error_type` | Количество ошибок       |
| `http_request_duration_seconds`                   | Histogram | `method`, `endpoint`               | Время обработки запроса |


- Prometheus **реально собирает метрики** (настроен `scrape_config`).

- Prometheus поднимается в `docker-compose`.

> Студент самостоятельно выбирает клиентскую библиотеку Prometheus для
> своего языка и проектирует middleware/interceptor для автоматического
> сбора метрик.

## **5–7 баллов**

### **5. Grafana: дашборды сервисов (1 балл)**

Необходимо создать дашборды в Grafana для визуализации метрик ваших
сервисов.

**Требования:**

- Отдельный дашборд (или секции) для **каждого вашего сервиса**.

- Видны метрики:

  - **latency** — перцентили p50, p95, p99

  - **errors** — error rate или error count

  - **throughput** — requests per second

- Минимум **4 панели** на дашборде (типы панелей студент выбирает
  самостоятельно: line chart, gauge, heatmap, stat, bar chart и т.д.).

- Дашборд обновляется в реальном времени.

- Дашборд экспортирован в JSON и хранится в репозитории.

- Grafana поднимается в `docker-compose` с автоматическим provisioning
  дашбордов и datasource.

------------------------------------------------------------------------

### **6. Grafana: дашборд инфраструктуры (1 балл)**

Необходимо создать отдельный дашборд для мониторинга инфраструктуры
вашей системы.

**Требования:**

- Отдельный дашборд для компонентов, которые использует ваша система.
  Набор панелей зависит от вашего стека:

|                |                                                    |
|----------------|----------------------------------------------------|
| Компонент      | Примеры метрик                                     |
| **Kafka**      | consumer lag, partition count, broker status       |
| **ClickHouse** | insert rate, query rate, memory usage              |
| **Cassandra**  | read/write latency, pending compactions            |
| **Redis**      | memory usage, connected clients, ops/sec, hit rate |
| **PostgreSQL** | active connections, query rate, cache hit ratio    |


- Дашборд должен отвечать на вопрос: **«Где сейчас узкое место?»**

- Минимум **3 панели** с метриками инфраструктурных компонентов.

- Дашборд экспортирован в JSON и хранится в репозитории.

> Как именно экспортировать метрики из инфраструктурных компонентов (JMX
> exporter, встроенные метрики, сторонние экспортеры) — студент решает
> самостоятельно.

------------------------------------------------------------------------

### **7. Нагрузочное тестирование, интегрированное в CI (1 балл)**

Необходимо добавить нагрузочное тестирование в CI pipeline.

**Требования:**

- Реализован нагрузочный тест (инструмент на выбор: **k6**, **hey**,
  **locust** или аналог).

- Тест запускается **из CI** (автоматически, как шаг пайплайна).

- Тест создаёт **реалистичную нагрузку** (не один запрос, а поток:
  минимум 10 VU, минимум 30 секунд).

- Определены **пороги** (thresholds): при превышении тест возвращает
  exit code 1 и CI падает.

- Под нагрузкой сервис **остаётся доступным** (health check проходит).

- Логи/результаты нагрузочного теста сохраняются как артефакты
  пайплайна.

## **8–10 баллов**

### **8. E2E + нагрузка + метрики в одном CI прогоне (1 балл)**

Необходимо реализовать комплексный CI сценарий, который запускает
систему, нагружает её и проверяет метрики из Prometheus.

**Требования:**

- CI сценарий:

  1.  Поднимает всю систему (`docker-compose up`).

  2.  Запускает нагрузку.

  3.  **Параллельно собирает метрики** из Prometheus.

  4.  **Проверяет числовые условия** по метрикам, например:

      - `error rate < 1%`

      - `p95 latency < 500ms`

- CI **падает**, если условия не выполнены.

- Метрики и результаты проверки сохраняются в артефакты пайплайна.

> Конкретные запросы к Prometheus API, скрипты проверки и пороговые
> значения — студент проектирует самостоятельно. Пороги должны быть
> обоснованы (не взяты с потолка).

### **9. Prometheus alert rules как код (1 балл)**

Необходимо определить alert rules для мониторинга проблем вашей системы.

**Требования:**

- Определены alert rules минимум для **двух** из следующих ситуаций:

  - **Высокий error rate** (например, \> 5% за 5 минут)

  - **Высокая latency** (например, p95 \> 1s за 5 минут)

  - **Consumer lag** (если используете Kafka)

  - **Недоступность сервиса** (target down)

- Alert rules **хранятся в репозитории** (`alerts.yml` или аналогичный
  файл).

- Alertmanager поднимается в `docker-compose`.

- Продемонстрировано, что при превышении порога алерт **реально
  срабатывает** (переходит в состояние `firing`).

- Алерты видны в UI Alertmanager или Grafana.

> Конкретные PromQL-выражения, пороги и `for`-длительности студент
> определяет самостоятельно, исходя из характеристик своей системы.

### **10. System-level SLI и пороги отказа (1 балл)**

Необходимо определить SLI (Service Level Indicators) для всей вашей
системы и показать, как они используются.

**Требования:**

- Определены **2–3 SLI всей системы**. Примеры возможных SLI (студент
  выбирает подходящие для своей системы):

  - **End-to-end latency** — время от запроса клиента до ответа

  - **Event processing delay** — время обработки события от публикации
    до потребления

  - **API availability** — процент успешных запросов

- Для каждого SLI определены:

  - **SLO** (целевое значение) — при каком значении система работает
    нормально

  - **Порог отказа** — при каком значении система считается
    «сломавшейся»

|                         |          |              |
|-------------------------|----------|--------------|
| SLI                     | SLO      | Порог отказа |
| Пример: API latency p95 | \< 500ms | \> 1000ms    |
| Пример: Availability    | \> 99.5% | \< 95%       |


- SLI **считаются из метрик Prometheus** (не hardcoded значения, а
  реальные PromQL-запросы).

- SLI **используются** в тестах или алертах (при пересечении порога
  отказа CI падает или срабатывает алерт).

- SLI задокументированы в README: что измеряется, какой запрос к
  Prometheus, целевые значения, обоснование порогов.
